04

What went wrong, in order

Eight independent faults, each one masking the next. They're numbered because that's how they surfaced — fixing one exposed the one beneath it.

1

The subnet was a /29

A /29 gives only 6 usable addresses. Any device numbered above .6 was, by its own mask, on a different network — so the router (the gateway) could reach a host that the switches and desktop could not.

fixWidened the mask to /28 so every device counts as a neighbour. Verify it's /28 on every host, not just some.
2

CRS305 didn't commit the new VLAN to hardware

A freshly-added Bridge VLAN row showed the right tagged ports but an empty current-tagged — the hardware-offloaded switch chip never programmed it, so the VLAN existed on paper and switched nothing.

fixRe-apply the entry (Apply in WinBox / re-run the set) to force the chip to reprogram. Trust current-tagged, not tagged.
3

Two identical switches, both named “MikroTik”

AG01 and AG02 are the same CRS305 model on default identities — one keystroke from configuring the wrong box and breaking the one that worked.

fixAlways confirm by IP / bridge name before touching anything: AG01 = .99.4, AG02 = .99.5. (Worth setting real identities.)
4

Every bridge port was PVID 1 + admit-all

With pvid=1, untagged traffic landed in VLAN 1 instead of its intended VLAN, and admit-all with ingress-filtering off meant the switch enforced nothing. VLANs looked configured but never classified traffic.

fixAccess ports: pvid=<vlan>, ingress-filtering=yes. Trunks: pvid=1, frame-types=admit-only-vlan-tagged.
5

VLAN 99 on two uplinks = a bridging loop

Adding VLAN 99 to both AG01 ether1 and sfp-sfpplus1 gave it two parallel paths to the router. The router's per-VLAN vlan-unaware bridges run separate STP instances, so nothing blocked the loop.

fixCarry each VLAN on exactly one path to the router. Mgmt rides ether1↔ether2 only; the data trunk stays data-only.
6

Copper SFP in an SFP+ cage

The RJ45 SFP feeding the TV wouldn't behave: auto-neg on dropped the link (the cage can't negotiate the module's host side), and forcing it created a duplex mismatch — DHCP completed but sustained traffic drowned in late collisions.

doneCopper handed to a switch that does copper: the ASUS now sits on AG02 sfp-sfpplus3 at forced 1G full, and the TV came up instantly. The ASUS runs the auto-neg down to the TV that the SFP+ cage never could.
7

“The switch can't ping the VM”

A red herring. An L2 switch can only source a ping from an IP it holds — AG01 had no address on VLAN 10. The data path was fine the whole time (AG02's pings crossed AG01 to reach the VM).

fixAdd an SVI / DHCP client on the VLAN only to test from the switch — and set add-default-route=no so it doesn't hoard default routes.
8

Desktop → VM: a stale firewall address

The real one. The admin address-list held the desktop's old IP .14, but DHCP had drifted it to .9, so the “admin desktop → all VLANs” accept rule never matched. It “used to work” because the desktop used to be .14.

fixPointed the list at 192.168.5.9 and made the desktop's lease static so its IP can't drift and silently re-break this.
05

Open housekeeping

Nothing here is breaking traffic today — these are the loose ends to tidy when you feel like it.

  • AG02 sfp-sfpplus1 PVID 5 → 1
    The trunk to AG01 sits at PVID 5 while AG01's side is PVID 1 — a native-VLAN mismatch. Tagged traffic is fine; set it to pvid=1 + admit-only-vlan-tagged to close it.
  • AG01 diagnostic DHCP clients
    The per-VLAN DHCP clients added to test each get a default route. Set add-default-route=no, or remove them and keep only the mgmt IP on VLAN 99.
  • Leftover L3 VLAN interfaces
    Stray vlan5 / vlan10 / vlan30 interfaces on the switches — only mgmt99 is needed. Harmless clutter; remove when convenient.
  • Set real device identities
    Rename the CRS305s off “MikroTik” to AG01 / AG02 so the two-identical-switches trap can't bite again.
